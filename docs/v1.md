# What v1.0 means

**Status: draft.** Nothing here is decided until the open decisions at the end
are answered; each one carries a recommendation. Once they are, this page is
the definition a v1.0 tag is checked against.

Before v1.0 a release may remove or change exported identifiers, and
[CHANGELOG.md](../CHANGELOG.md) names each one. v1.0 ends that: it is a promise
about what will not change. This page says what the promise covers, what it
leaves out, and what must be true before the tag is made.

## The promise

From v1.0.0, for every package the promise covers:

- No exported identifier is removed, renamed or given a different signature.
  A change that would break a program that compiled against v1.0.0 waits for
  v2.
- An exported identifier may be deprecated. It keeps working for the rest of
  v1.
- Behaviour a doc comment states does not change. Behaviour no doc comment
  states may, when the old behaviour was a bug.
- [api.txt](../api.txt) is the list of what is covered. The `api` CI job
  already fails when a line of it is removed or changed without a
  `- BREAKING:` entry; from v1.0.0 it fails on any such change in a covered
  package, entry or not.

New identifiers, new packages, and new fields on structs meant to be built
with field names arrive in minor releases (v1.1, v1.2). Fixes arrive in patch
releases.

## What the promise covers

Packages are at one of three levels today, listed in the
[README](../README.md) and in the package comment of each:

| Level | Packages | In the promise |
|---|---|---|
| Core | `tui`, `ansi`, `layout`, `theme`, `term`, `motion`, `input`, `keymap`, `hittest`, `tuitest` | Yes |
| Stable-ish | `cellbuf`, `widgets`, `widgets/chart`, `markdown`, `focus` and 37 components | Yes, renamed Stable (decision 1) |
| Experimental | 10 packages, below | No |

## What it leaves out

- **Experimental packages.** A package whose comment says
  `Stability: experimental.` may change or disappear in any minor release.
  Each change is still a `- BREAKING:` entry in the changelog.
- **Everything under `internal/`**, which no other module can import.
- **`examples/`, `bench/` and `site/`.** They are programs and pages, not API.
- **The bytes written to the terminal.** The promise is about what a frame
  shows, not which escape sequences draw it. A release may draw the same
  screen with different bytes, so a test that compares raw output can break;
  one that reads the screen through `tuitest` does not.
- **Exact rendered text of widgets.** A widget's spacing, glyphs and colours
  may be corrected in a minor release. Golden files of a widget's `View` may
  need regenerating; the changelog says when.
- **Timing.** Frame pacing, tick coalescing and how many `Update` calls a
  burst of input produces are not promised.
- **A minimum Go version.** It may rise in a minor release, never past the
  older of the two newest Go releases (decision 5).

## Experimental packages

Each of the ten needs one of three outcomes before v1.0: promote it into the
promise, keep it experimental, or remove it from the module. Evidence as of
2026-10-08: ACLine is the only known program outside this repository that
imports tui, and of these ten it imports only `commandpalette`.

| Package | Outside user | Recommendation |
|---|---|---|
| `commandpalette` | ACLine | Promote, after its deprecated `Init` is removed |
| `clipboard` | none | Keep experimental |
| `notificationcenter` | none | Keep experimental; it has `Render(base)` where every other component has `Update` and `View` |
| `imageview` | none | Keep experimental; it has no `Update` |
| `appshell` | none | Keep experimental |
| `streamtext` | none | Keep experimental |
| `toolapproval` | none | Keep experimental |
| `errorretry` | none | Keep experimental |
| `faces` | none | Keep experimental |
| `avatar` | none | Keep experimental |

A package nobody outside has used has an API nobody has tested by using it.
Keeping it experimental costs nothing and leaves room to fix what its first
real user finds.

## Before the tag

v1.0.0 is tagged when all of these hold. Each is a check, not a judgement.

1. **No deprecated identifier is exported.** Thirteen are today: `layout.Box.Render`,
   `ansi.SetClusterWidth`, `textinput.Model.ClipboardWrite`,
   `textarea.Model.ClipboardWrite`, `autocomplete.Model.Init`,
   `commandpalette.Model.Init`, and seven chart forwards in `widgets`
   (`BarChart`, `Gauge`, `HeatMap`, `LineChart`, `Sparkline`, `SparklineWith`,
   `BarItem`). They are removed in the last v0 release, with a `- BREAKING:`
   entry each. No package of the library calls one that another package
   exports; the `staticcheck` CI job fails if one does. `layout.BoxNode` is
   still built on `Box.Render` inside package `layout`, so removing that
   method means making it unexported, not deleting it.
2. **Every experimental package has its outcome**, and the `Experimental:`
   list in [doc.go](../doc.go) matches.
3. **CI is green** on Linux, macOS, Windows and FreeBSD, with `staticcheck`,
   `gosec`, the coverage floor and the `api` job.
4. **The last v0 release has been used.** ACLine builds and passes its tests
   against it, with no workaround in ACLine for a tui defect.
5. **Every covered package has been used from outside its own tests**
   (decision 2): by ACLine, or by a program under `examples/`. Today 24
   packages are imported by no example program, and ACLine imports 16 packages
   and the root.
6. **The docs are enough to build from.** A first tutorial exists that goes
   from an empty directory to a working program, and
   [migrating-to-v1.md](migrating-to-v1.md) names a replacement for every
   identifier removed since v0.1.0.
7. **A release candidate has been out for a week** (decision 4) with no
   breaking change needed.

## After v1.0

- A covered package that turns out to be wrong is fixed by adding the right
  API beside the old one and deprecating the old one, never by changing it.
- An experimental package is promoted in a minor release, by removing the
  `Stability: experimental.` line. Promotion is one-way.
- v2 would be a new module path, with a `/v2` suffix, and is not planned.

## Open decisions

1. **Does "Stable-ish" become "Stable" and enter the promise?** The 42
   packages at that level hold most of the API, and ACLine uses 12 of them.
   - Recommended: yes, for each one that passes item 5 above; mark the rest
     experimental until they do. That uses the level the project already has,
     and keeps the promise to what has been exercised.
   - Alternative: all 42 enter the promise as they are. Simpler to state, and
     freezes an API of which most has had no user outside this repository.
2. **Is "used from outside its own tests" a condition of the promise?** That
   is item 5.
   - Recommended: yes, with an example program counting as use. It turns the
     24 missing examples into release work with a clear end.
   - Alternative: no condition; trust the tests and the 90% coverage floor.
3. **Is v1.0 tagged by date or by condition?** The goal on record is
   2026-10-31.
   - Recommended: by condition, with the date as the target. If item 4, 5 or 7
     is not met on the day, the tag waits and a v0 release goes out instead.
   - Alternative: by date, narrowing the promise (more packages experimental)
     until what is left meets the conditions.
4. **How long does a release candidate stay out?**
   - Recommended: one week, tagged `v1.0.0-rc.1`, used by ACLine for that
     week.
5. **Which Go versions are supported?** `go.mod` says 1.25 and CI tests on
   1.25.
   - Recommended: the two newest Go releases, as Go itself supports; CI tests
     on both.
6. **Do experimental packages stay in this module?**
   - Recommended: yes. A second module would need a `require` on this one,
     and one module with a stated exception is simpler than two.
   - Alternative: move them to a nested module, so the module's version means
     the same thing for every package in it.
